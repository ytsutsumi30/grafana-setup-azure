# アプリ改善・優先対応・検証ループ

更新日: 2026-07-17

## 目的

出荷検品アプリの画面、API、データ、認証、テスト、運用性、技術的負債を横断して改善候補を確認し、根拠のある最優先項目を1件ずつ実装・検証する。

## ループ方式

- 手動で開始するゴールループとする。
- 1回につき改善は1件、対象画面は1つとする。
- 初回を含め最大3回、合計60分で停止する。
- 実装者と検証者を分離し、主観評価にはスクリーンショットによる人の確認を使う。

## 改善候補の選び方

計画書、現場レビュー、コード、テスト、画面、ログから3から5件の候補を抽出する。各項目を0から5で採点する。

```text
優先度 = セキュリティ・データ整合性 x 4
       + 業務影響 x 3
       + 発生頻度 x 2
       + テスト・運用性不足 x 1
       - 変更リスク x 2
       - 実装工数 x 1
```

セキュリティ侵害、データ消失、二重更新、数量不整合、再現する停止障害は最優先候補として扱う。同点なら小さく検証できるものを選ぶ。

## 実施手順

1. 対象業務と画面を再現し、改善候補と根拠を整理する。
2. 上位3件の点数を示し、今回実施する1件を確定する。
3. 正常系、異常系、回帰防止、監査を含む受入条件を最大5件定義する。
4. 対象ファイルだけを変更し、変更固有の関連テストを追加する。
5. 別の視点で差分をレビューし、検証ゲートを実行する。
6. 失敗時は修正後に検証を先頭から再実行する。
7. 成功後に画面証跡を確認し、結果と残存リスクを記録する。

## 必須検証ゲート

```bash
TARGET_PAGE=purchase-receiving \
RELATED_TESTS='tests/api/contract.test.js' \
bash scripts/verify-ui-change.sh
```

完了条件:

- dev stackが正常に起動する。
- 対象画面がHTTP 200で表示される。
- 対象画面のスクリーンショットが生成される。
- console error、pageerror、主要資産の読み込み失敗が0件である。
- HTTPスモーク、API構文検査、関連テストがすべて成功する。
- 人が業務導線、文言、視認性、誤操作リスクを確認する。

## 停止条件

3回失敗した場合は、失敗箇所、試した修正、証跡、残存リスクを報告して停止する。破壊的DB変更、本番データ操作、M365管理者作業、外部環境へのデプロイ、複数改善への拡大も人の判断へ戻す。

## 配置

- 上位ループ: `.agents/skills/app-improvement-loop/SKILL.md`
- UI改善サブループ: `.agents/skills/ui-improvement-loop/SKILL.md`
- 検証サブループ: `.agents/skills/ui-verification-loop/SKILL.md`
- 検証スクリプト: `scripts/verify-ui-change.sh`
- 実施記録: `docs/app-improvement-log.md`
- 画面証跡: `artifacts/ui-verification/`

## 実行例

```text
app-improvement-loopを使って、purchase-receiving画面に関係する業務からアプリを改善してください。
候補を採点し、最優先の1件だけを実装してください。
実装後は最大3回の検証ループを実行してください。
```
