# UI 改善・実装・検証ループ

更新日: 2026-07-17

アプリ全体から改善候補を選ぶ場合は、上位手順 `docs/app-improvement-loop.md` と `.agents/skills/app-improvement-loop/SKILL.md` を使用する。この文書はUI改善に範囲を限定したサブループである。

## 目的

出荷検品アプリの UI 改善を、思いつきの変更ではなく、現場影響の確認、改善候補の選定、受入条件の定義、実装、検証、記録まで一貫して進める。

## ループの単位

- 手動で開始するゴールループとする。
- 1 回につき対象画面は 1 つ、改善テーマは 1 つとする。
- 初回を含め最大 3 回、合計 45 分で停止する。
- 機械検証だけで完了とせず、スクリーンショットによる人の確認を最後に置く。

## 実施フロー

1. 対象画面と関連する計画、CSS、JavaScript、テストを確認する。
2. 変更前画面を確認し、業務影響、発生頻度、実装リスクから改善候補を比較する。
3. 最優先の 1 件を選び、最大 5 個の受入条件を実装前に定義する。
4. 対象範囲を広げずに実装し、必要な関連テストを追加する。
5. 実装者とは別の視点で差分を確認し、検証スクリプトを実行する。
6. 失敗時は原因を修正して検証を先頭から再実行する。
7. 成功後にスクリーンショットを人が確認し、結果をログへ記録する。

## 検証ゲート

```bash
TARGET_PAGE=shipping-instructions \
RELATED_TESTS='tests/api/contract.test.js' \
bash scripts/verify-ui-change.sh
```

完了には、次の全条件を満たす必要がある。

- Docker Compose の dev stack が起動する。
- 対象画面が HTTP 200 で表示される。
- 対象画面のスクリーンショットが保存される。
- console error、pageerror、主要資産の読み込み失敗が 0 件である。
- HTTP スモークテストが成功する。
- API 構文検査と指定した関連テストが成功する。
- 人が画面の情報設計、業務導線、日本語文言、視認性を承認する。

## 停止とエスカレーション

3 回失敗した場合は継続せず、失敗箇所、試した修正、ログ、残存リスクを報告する。M365 認証、業務判断、テストデータ、複数画面へまたがる仕様変更が必要な場合も、人の判断へ戻す。

## 在庫・ロット・QR基盤 先進UIループ（2026-07-18）

- 形式: 手動開始のゴールループ。
- 完了条件: 優先改善を1件ずつ実装し、デスクトップと390pxで表示崩れなし、console error 0件、関連UIテスト成功。
- 上限: 最大10ループ。今回は実装7ループと統合検証1ループの計8ループ。
- 実装範囲: `web/inventory-foundation.html`、ページCSS・JS、共通トークン・ヘッダー、専用UIテスト。
- ガードレール: 外部CDN追加禁止、ページ内style禁止、業務データのlocalStorage保存禁止、48pxタッチ領域維持、API・DB更新なし。
- 検証: ローカルdev server、Playwright APIモック、1440px・390pxスクリーンショット、console/pageerror、横方向overflow、JS構文、API構文。
- 停止条件: 最大10回到達、認証や外部サービスにより再現不能、業務仕様の追加判断が必要、または同一検証が3回連続失敗。

## 実行例

```text
ui-improvement-loopを使って、shipping-instructions画面を改善してください。
改善案が未指定なら現状を調査し、最優先の1件だけを選んでください。
受入条件を先に定義し、実装後は最大3回の検証ループを実行してください。
```
