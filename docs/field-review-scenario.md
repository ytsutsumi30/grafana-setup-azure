# 出荷検品アプリ 現場レビュー操作シナリオ

作成日: 2026-07-08

## 目的

現場レビュー当日に、参加者が同じ操作順で POC を確認できるようにする。

このシナリオは `docs/field-review-checklist.md` と併用する。

## 利用環境

公開 URL:

```text
https://shipping-inspection-poc-web.lemonmushroom-c9d1cf36.japaneast.azurecontainerapps.io/index.html
```

前提:

- M365 ログイン済みブラウザで操作する。
- API は画面から Bearer token 付きで呼び出される。
- HTML 印刷またはブラウザ PDF 保存ができる端末で確認する。

## レビュー対象画面

| 目的 | 画面 |
|------|------|
| ホーム | `/index.html` |
| 出荷指示一覧 | `/shipping-instructions.html` |
| PPS / 出荷作業 | `/pps.html` |
| 出荷履歴 | `/shipping-history.html` |
| 出荷検品結果票 | `/shipping-report.html?type=inspection_result` |
| ロット別出荷実績票 | `/shipping-report.html?type=lot_shipment` |

## 事前データ

レビュー前に、少なくとも次のデータを用意する。

| シナリオ | 必要データ |
|----------|------------|
| 正常出荷 | 複数品目、複数ロットを含む未完了の出荷指示 |
| NG 検品 | 未引当ロット、別品目、QR 不明の確認用 QR |
| 重複検品 | 同一 QR を複数回スキャンできる確認用 QR |
| 完了後修正 | 出荷完了済みで、ロットまたは数量を修正する対象 |
| 帳票再発行 | 出荷完了済みで、帳票を複数回出力する対象 |

## シナリオ 1: ログインと初期表示

目的:

M365 ログイン後、アプリの初期画面と主要導線を確認する。

操作:

1. 公開 URL を開く。
2. M365 ログインを実行する。
3. ホーム画面を表示する。
4. 出荷指示、PPS、QRコード読み取り、メンテナンス、出荷履歴への導線を確認する。

期待結果:

- ログインが完了する。
- ホーム画面が表示される。
- データ読込エラーが出ない。
- 保護対象 API は未ログイン時に `401` になる。

記録する観点:

- ログイン操作で迷う箇所
- ホーム画面で不足している情報
- ボタン名、表示名、現場用語とのずれ

## シナリオ 2: 出荷指示選択

目的:

出荷指示一覧からレビュー対象の出荷指示を選択できるか確認する。

操作:

1. `/shipping-instructions.html` を開く。
2. レビュー対象の出荷指示を検索または一覧から選択する。
3. 顧客名、出荷予定日、ステータス、品目数を確認する。
4. PPS / 出荷作業へ進む。

期待結果:

- 対象の出荷指示を見つけられる。
- 複数品目の出荷指示であることが分かる。
- 単一品目データも互換表示される。

記録する観点:

- 検索条件として不足している項目
- 一覧に追加すべき列
- ステータス表示の分かりやすさ

## シナリオ 3: 品目別ロット引当と数量確定

目的:

出荷指示内の品目ごとにロットを選択し、数量確定できるか確認する。

操作:

1. `/pps.html?id=<出荷指示ID>` を開く。
2. 1 件目の品目を選択する。
3. 対象品目のロット一覧を確認する。
4. 適正ロットを選択する。
5. 出荷数量を入力する。
6. 数量を確定する。
7. 未確定品目が残っている場合、次の品目で同じ操作を行う。
8. 全品目の数量確定後、PPS / QR 検品へ進む。

期待結果:

- 品目ごとにロット候補が切り替わる。
- ロット番号、数量、保管場所が確認できる。
- 数量確定後に次の品目へ誘導される。
- 全品目確定後に PPS / QR 検品へ進める。

記録する観点:

- ロット選択に必要な情報が足りているか
- 数量入力の桁、単位、初期値
- 未確定品目への誘導の分かりやすさ

## シナリオ 4: QR 検品 OK

目的:

確定済みロット引当に対して、正しい QR をスキャンし、数量を入力して OK 登録できるか確認する。

操作:

1. PPS / QR 検品画面で QR 読み取りを開始する。
2. 確定済みロットに該当する QR をスキャンする。
3. スキャン直後に数量を入力する。
4. 検品 OK として登録する。
5. 品目別、ロット別の進捗が更新されることを確認する。

期待結果:

- QR スキャン後に数量入力できる。
- 入力数量が OK 数量へ加算される。
- 残数量が更新される。
- 監査ログに QR 検品イベントが記録される。

記録する観点:

- スキャンから数量入力までの操作時間
- 数量入力のしやすさ
- 検品 OK 後のフィードバック

## シナリオ 5: QR 検品 NG / 重複

目的:

未引当ロット、別品目、重複スキャンが期待通り扱われるか確認する。

操作:

1. 未引当ロットの QR をスキャンする。
2. 別品目の QR をスキャンする。
3. 一度 OK 登録した QR を再度スキャンする。
4. NG 理由分類とコメントを入力する。
5. 検品数量に加算されないことを確認する。

期待結果:

- 未引当ロットは NG として記録される。
- 別品目は NG として記録される。
- 重複スキャンは警告され、追加カウントされない。
- NG 理由分類とコメントが監査ログに残る。

記録する観点:

- 警告文の分かりやすさ
- NG 理由分類の過不足
- コメント入力の必要度と負担

## シナリオ 6: 出荷完了

目的:

確定済みロット引当の全数量が QR 検品 OK になった場合に、出荷完了できるか確認する。

操作:

1. 全品目、全ロットの必要数量を OK 登録する。
2. 出荷完了条件を確認する。
3. 出荷完了操作を実行する。
4. 完了後、出荷履歴画面へ遷移する。

期待結果:

- 未完了の品目、ロット、数量がないことが分かる。
- 出荷完了できる。
- ステータスが出荷済みになる。
- 出荷完了イベントが監査ログに残る。

記録する観点:

- 出荷完了ボタンの位置と表示
- 誤操作防止の確認表示
- 完了後に現場が確認したい情報

## シナリオ 7: 出荷履歴と監査ログ

目的:

出荷完了後に、出荷指示、品目、ロット、QR / スキャン、監査ログを追跡できるか確認する。

操作:

1. `/shipping-history.html?id=<出荷指示ID>` を開く。
2. 品目別タブを確認する。
3. ロット別タブを確認する。
4. QR / スキャン単位の履歴を確認する。
5. 監査ログを確認する。

期待結果:

- 出荷指示単位で履歴を確認できる。
- 品目別、ロット別、QR / スキャン単位で追跡できる。
- 出荷完了、NG、重複、帳票出力、完了後修正のイベントが確認できる。

記録する観点:

- 検索、絞り込み、ページングに必要な条件
- 表示順の妥当性
- 監査ログの表現の分かりやすさ

## シナリオ 8: 完了後修正

目的:

出荷完了後の数量またはロット修正が、理由付きで監査ログに残るか確認する。

操作:

1. 出荷済みの出荷指示を開く。
2. 完了後修正の操作を実行する。
3. ロットまたは数量を変更する。
4. 理由分類とコメントを入力する。
5. 履歴画面で修正前後の差分を確認する。
6. 帳票が修正版として表示されることを確認する。

期待結果:

- 修正理由が必須になる。
- 修正前後が監査ログに残る。
- 履歴画面で差分を読める。
- 帳票が修正版または修正版・再発行として識別できる。

記録する観点:

- 完了後修正を許可する業務条件
- 承認者確認が必要か
- 理由分類の過不足

## シナリオ 9: 帳票出力

目的:

出荷検品結果票とロット別出荷実績票を HTML 印刷 / PDF 保存できるか確認する。

操作:

1. 出荷履歴画面から出荷検品結果票を開く。
2. 帳票内容を確認する。
3. 印刷プレビューを開く。
4. ブラウザ PDF 保存を実行する。
5. ロット別出荷実績票でも同じ確認を行う。
6. 帳票を再出力し、再発行番号が変わることを確認する。

期待結果:

- 出荷検品結果票が表示される。
- ロット別出荷実績票が表示される。
- 帳票番号、版数、発行履歴が表示される。
- HTML 印刷と PDF 保存でレイアウトが崩れない。
- 帳票出力イベントが監査ログに残る。

記録する観点:

- 帳票に追加すべき項目
- 不要な項目
- 承認欄の運用
- 用語、表示順、改ページ

## シナリオ 10: 監視 / 障害時確認

目的:

POC 運用時に最低限の稼働確認と問い合わせ切り分けができるか確認する。

操作:

1. `/health` を確認する。
2. `/api/auth/m365/config` を確認する。
3. Azure Container Apps の API / Web revision と Running 状態を確認する。
4. Application Insights / Log Analytics の確認方法を共有する。

期待結果:

- Web が稼働していることを確認できる。
- API が M365 設定を返すことを確認できる。
- 未認証の保護対象 API が `401` になる。
- 障害時の一次確認先が分かる。

記録する観点:

- 現場で必要な問い合わせ情報
- 監視対象メトリクス
- 障害時の暫定運用
