# Refactor(振る舞い保存の段階的改善)

## DO(やること)

- 黄金律: 振る舞い保存 / 小さな一歩 / 各ステップ後にテスト / 安全な状態でコミット / 一度に1種類の変更。
- 着手前に対象のコードスメルを特定し、技法を選ぶ:
  Long Method→関数抽出 / 重複コード→共通化 / God Class→責務ごとに分割 / 長い引数リスト→パラメータオブジェクト(複雑ならBuilder) / Feature Envy→ロジックをデータ所有側へ移動 / Primitive Obsession→ドメイン型 / マジックナンバー→名前付き定数 / ネスト条件→早期return・ガード節。
- 既存のテストフロー・コミット規約に従い、各ステップでテスト実行。

## DON'T(やらないこと)

- リファクタと機能変更・バグ修正の混在。
- テスト無しでの大規模変更(その場合は先に特性テストを提案)。
- 全面書き直し(このSkillの対象外。要件が変わる場合はPRDへ)。
- 触る理由のない箇所への美観だけを理由にした広範囲変更。

## OUTPUT FORMAT(出力の型)

1. リファクタ計画表: スメル → 適用技法 → 対象ファイル → リスク
2. ステップごとの差分(小さく)+ 各ステップのテスト結果
3. 完了サマリー(変更前後の構造、振る舞い不変の根拠)
